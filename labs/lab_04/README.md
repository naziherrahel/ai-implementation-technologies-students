# Lab 04 — Make One Inference Path Run

Today your team will turn its existing baseline into a small inference demo. The demo will accept one input, return a structured response, and save a record of what happened. You will also create a diagram that matches the path used by the code.

## Start with the existing project

Open:

- the Lab 02 baseline code and `reports/baseline_metrics.json`;
- `docs/project_decisions.md` from Lab 03.

Use these files when choosing the input, result, and user action for the demo.

## What you should have before leaving

```text
README.md                              one run instruction for the demo
docs/
  inference_architecture.drawio       editable architecture diagram
reports/
  inference_demo.jsonl                generated by the demo
src/
  inference_demo.py                   or notebooks/inference_demo.ipynb
```

The handout includes a Python starter and an editable diagrams.net template. You may use another editable diagram format if your team already works with one.

## 1. Choose the path — 5 minutes

Choose:

- **Trigger:** when prediction starts—during a scheduled batch, after a user request, or from a continuous stream.
- **Intended placement:** where the prediction code is intended to run—on a shared computer or server, on the input device, or split between both.

Put these two choices at the top of the diagram. Choose what fits the project; you do not need to compare every option.

The **inference boundary** is the point where accepted input enters the prediction code and a structured response comes back. A structured response uses named fields such as `request_id`, `status`, `result`, and `action`.

## 2. Connect the baseline — 30 minutes

Copy [`starter/inference_demo.py`](starter/inference_demo.py) into the team project as `src/inference_demo.py`, or build the same path in a notebook.

Adapt `project_predict()` so it uses the prediction step from the Lab 02 baseline. Reuse the current model; do not train or tune another model today. If the baseline script only saves an overall metric, use the predictions created immediately before that metric is calculated.

The function should return a small dictionary:

```python
{"result": "project-specific result", "needs_review": False}
```

- `result` can be a string, number, list, or simple dictionary.
- Set `needs_review` to `False` when the result can follow the normal path.
- Set it to `True` when a person should check the result before it is used.

Update these values in the starter:

- `MODEL_VERSION`: a short label for the current model, such as `baseline-v1`;
- `RULE_VERSION`: a short label for the current decision logic, such as `decision-v1`;
- `NORMAL_ACTION`: what happens after a normal result;
- `REVIEW_ACTION`: what happens when a person should check the result;
- `UNAVAILABLE_ACTION`: what happens when prediction cannot run.

Keep each action short and specific, for example `show the result`, `ask for a manual check`, or `try again later`.

## 3. Run the safe failure case — 10 minutes

The starter runs the input twice:

1. a normal attempt using `project_predict()`;
2. a controlled attempt in which inference is marked as unavailable.

For the second attempt, the result is `null`, the status is `unavailable`, and the program uses `UNAVAILABLE_ACTION`. The record also contains `"simulated": true`, showing that this was an intentional classroom test rather than a real outage.

A `review` status means prediction ran but a person should check the result. An `unavailable` status means prediction did not run.

## 4. Generate and inspect the evidence — 10 minutes

Add the demo run instruction to the project `README.md`.

On macOS or Linux, run:

```bash
python3 src/inference_demo.py --input-ref path/to/one/example
```

On Windows PowerShell, run:

```powershell
py src/inference_demo.py --input-ref path/to/one/example
```

If Windows does not recognize `py`, use `python` instead.

The run must create `reports/inference_demo.jsonl` with two lines: one normal attempt and one simulated unavailable attempt. A notebook must run from top to bottom and create the same file.

Each line contains:

- `request_id` — a unique identifier for the attempt;
- `input_ref` — a safe reference to the input, not private raw data;
- `status` — `ok`, `review`, or `unavailable`;
- `result`;
- `model_version` and `rule_version`;
- `latency_ms` — how many milliseconds the attempt took;
- `action`;
- `simulated` — `true` only for the controlled unavailable attempt.

Example:

```json
{"request_id":"...","input_ref":"sample/night_01.jpg","status":"ok","result":"fire","model_version":"baseline-v1","rule_version":"decision-v1","latency_ms":84.2,"action":"show alert to operator","simulated":false}
{"request_id":"...","input_ref":"sample/night_01.jpg","status":"unavailable","result":null,"model_version":"baseline-v1","rule_version":"decision-v1","latency_ms":0.1,"action":"use manual inspection","simulated":true}
```

Use values and actions that fit your project.

## 5. Draw the same path — 15 minutes

Copy [`starter/inference_architecture.drawio`](starter/inference_architecture.drawio) into the team project as `docs/inference_architecture.drawio`, then replace its placeholder labels.

The diagram should show:

1. the real input source;
2. one basic input check already used by the baseline;
3. preprocessing;
4. the current baseline or model;
5. the decision step;
6. the person or component that receives the response and the action it takes;
7. the unavailable path and its safe action;
8. the evidence record connected by `request_id`.

Label the inference boundary and where the main components are intended to run. Label arrows with the input, result, response, or action they carry. Include only components that the project is intended to use.

## 6. Run, trace, and commit — 15 minutes

Run the demo and open `reports/inference_demo.jsonl`. Confirm that it contains one normal record and one simulated unavailable record.

Ask a teammate to trace:

1. the normal input from its source to the action and matching evidence line;
2. the unavailable attempt to its safe action and matching evidence line.

Correct any disagreement between the code, generated records, and diagram. Then show me the run, the two records, and the diagram, and commit the Lab 04 work.

## Lab 04 is complete when

- the demo uses the existing baseline to produce a real result;
- one documented run creates both JSONL records;
- the unavailable record is clearly marked as simulated;
- the editable diagram matches the code, response fields, actions, and evidence;
- a teammate can trace both paths directly from the diagram and evidence file.
